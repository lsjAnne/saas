# 部署与环境配置说明

## 1. 文档目的
本文档定义平台的环境分层、部署组件、配置分类、构建基线、联调网络口径和交付要求，作为标准 SaaS 版与私有化版的软件部署基线。

## 2. 环境分层
| 环境 | 主要用途 | 关键要求 |
| --- | --- | --- |
| 开发环境 | 本地开发、自测、快速验证 | 可重置、可局部 Mock、支持快速构建 |
| 联调环境 | 前后端、第三方、模型能力联调 | 固定账号、稳定种子数据、基础审计可用 |
| 测试环境 | 回归验证、自动化执行、验收预演 | 数据可复用、权限完整、日志可追踪 |
| 预发环境 | 上线前验证 | 配置尽量接近生产、禁止临时绕过鉴权 |
| 生产环境 | 正式业务运行 | 安全注入、备份、监控、告警、审计全部启用 |

## 3. 标准交付形态
### 3.1 SaaS 标准版
- 平台统一托管部署。
- 多租户共享应用与基础设施。
- 通过租户、组织、权限、配额和审计隔离。

### 3.2 私有化版
- 单客户独立环境部署。
- 配置、数据、监控、备份和访问控制独立管理。
- 与标准版共用统一业务模型、接口模型和审计模型。

## 4. 标准部署组件
| 组件 | 职责 | 标准 SaaS 版 | 私有化版 |
| --- | --- | --- | --- |
| Web 前端 | 租户业务前台与平台后台入口 | 必选 | 必选 |
| API 主服务 | 主业务接口、平台接口、开放接口 | 必选 | 必选 |
| Job Worker | 定时任务、巡检、对账、清理、补偿 | 必选 | 必选 |
| Callback Worker | 外部回调消费、重试、补偿 | 必选 | 按集成场景启用 |
| AI Worker | 模型异步生成、评测、脚本任务 | 按能力启用 | 按能力启用 |
| PostgreSQL | 主业务库 | 必选 | 必选 |
| Redis | 缓存、幂等、会话短状态 | 必选 | 必选 |
| MQ | 异步削峰、通知、回调解耦 | 按业务能力启用 | 按业务能力启用 |
| 对象存储 | 素材、导出文件、附件 | 按业务能力启用 | 按业务能力启用 |
| 观测栈 | 日志、指标、告警、追踪 | 必选 | 必选 |
| 前端网关（nginx） | 托管前端静态资源、反代 `/api` 与 `/actuator`、SPA 路由回退 | 必选 | 必选 |

## 5. 环境拓扑要求
### 5.1 标准运行拓扑
```text
Browser / Admin Console
        |
     Web Frontend
        |
      API Gateway / API Service
        |
  -----------------------------------------
  |           |            |               |
 PostgreSQL Redis        MQ        Object Storage
  |           |            |               |
 Job Worker  Callback Worker  AI Worker  Export / Asset Service
        |
 Observability Stack
```

### 5.2 拓扑控制要求
- 平台后台与租户业务前台必须逻辑分区。
- 平台侧接口、租户侧接口、开放接口、回调接口必须按域分层。
- 审计日志、导出文件、缓存 Key、异步任务都必须带 `tenant_id`。

## 7. 配置治理原则
- 业务参数与环境参数分离。
- 敏感信息通过环境变量、密钥管理系统或部署平台注入。
- 正式交付文档不记录真实密码、密钥、令牌和主机信息。
- 配置变更必须留痕、可回滚、可审计。
- 私有化版允许客户自管密钥，但不允许修改核心审计口径。

## 8. 当前工程运行基线
### 8.1 持久化策略
- 默认运行模式：`jdbc`
- 本地开发与自动化测试：优先使用 H2
- 联调和正式环境：使用 PostgreSQL

### 8.2 已落地 profile
- `default`：本地快速开发与单机验证
- `postgres`：直连联调数据库与缓存
- `tunnel-local`：本地通过 SSH 隧道接入远端数据库与缓存
- `server-local`：应用运行在与 PostgreSQL / Redis 同机的环境中；当前也作为本机 Docker 联调的固定 profile

### 8.3 凭据与密钥治理基线（2026-10 收紧）
- 生产 profile（`postgres`、`tunnel-local`、`server-local` 的生产配置段）不再包含明文密码/密钥：
  - 数据源账号密码：`${SPRING_DATASOURCE_USERNAME:}` / `${SPRING_DATASOURCE_PASSWORD:}`（无默认值，强制注入）
  - 认证密钥：`${APP_AUTH_TOKEN_SECRET:}` / `${APP_AUTH_BOOTSTRAP_PASSWORD:}`（无默认值，强制注入）
- 默认 profile 仅保留"本地可启动"级别的非明文弱值（长度 ≥ 32 的 token-secret、非默认 bootstrap 密码），启动时由 `AuthSecurityConfigVerifier` 提示生产部署必须覆盖
- `docker-compose` 中的密码均为部署占位默认值（如 `saas_password`），生产部署必须通过环境变量覆盖
- 自动化测试在 `backend/src/test/resources/application.properties` 中固定弱开发值（`123456` / `local-dev-auth-token-secret-change-me`），仅测试环境生效，不进入生产配置
- 明文保留范围：仅 `tunnel-local` / `server-local` 本地开发 profile 用于连接用户本地库的账号密码

## 9. 构建与启动基线
### 9.1 工具要求
- JDK：17（`pom.xml` 声明 `java.version=17`）
- Maven：3.9.x
- Node.js：22.x（前端构建）
- 禁止使用 Java 8 运行当前工程

### 9.2 本地构建基线
```powershell
$env:JAVA_HOME='D:\JDK'
$mavenHome='D:\maven\apache-maven-3.9.12'
$env:MAVEN_HOME=$mavenHome
$machinePath=[System.Environment]::GetEnvironmentVariable('Path','Machine')
$userPath=[System.Environment]::GetEnvironmentVariable('Path','User')
$env:Path="$env:JAVA_HOME\bin;$mavenHome\bin;$machinePath;$userPath"
mvn test
```

### 9.3 启动口径
- 本地开发默认使用 `default`，需要本机 Docker 联调时使用 `server-local`，需要 SSH 转发时使用 `tunnel-local`
- 联调环境使用固定 profile 和受控网络
- 预发与生产环境统一通过部署平台注入 profile 与密钥

## 10. 联调与网络基线
### 10.1 联调顺序
1. 本地默认环境自测
2. 联调环境固定数据验证
3. 通过 SSH 隧道接入远端数据库或缓存
4. 直接远端部署验证

### 10.2 SSH 隧道标准口径
```bash
ssh -L 15432:127.0.0.1:5432 -L 16379:127.0.0.1:6379 <user>@<host>
```

### 10.3 tunnel-local profile 使用方式
```bash
--spring.profiles.active=tunnel-local
```

### 10.4 本机 Docker 联调固定启动命令
```powershell
powershell -ExecutionPolicy Bypass -File .\scripts\start-dev-tunnel-local.ps1 -Mode server-local -EnableStage13Local
```

- 默认直连 PostgreSQL：`127.0.0.1:5432`，数据库：`postgres`，用户名：`username`，密码：`password`
- 默认直连 Redis：`127.0.0.1:6379`，密码：`mypassword`
- 如只需业务联调、不需要 `stage13-local` 本地探针，可去掉 `-EnableStage13Local`

## 11. 容器化部署与观测基线（2026-10 落地）
### 11.1 镜像与构建链路
| 产物 | 构建入口 | 说明 |
| --- | --- | --- |
| 后端镜像 | `Dockerfile` | OpenJDK 17 运行层；内置 `wget`；HEALTHCHECK 探测 `/actuator/health/liveness`（liveness，不依赖外部组件） |
| 前端镜像 | `Dockerfile.web` | 多阶段：node:22-alpine 构建（`npm ci` → `vue-tsc` + `vite build`），nginx:1.27-alpine 托管静态资源 |
| 镜像命名 | `APP_IMAGE_NAME` / `WEB_IMAGE_NAME` | 默认 `dian-shang-ping-tai:saas|private` / `dian-shang-ping-tai-web:saas|private` |
| CI 流水线 | `.github/workflows/backend-delivery.yml` | 新增 `frontend-build`（node 22 + `npm run build`）与 `build-web-image`（推送 GHCR `ghcr.io/<owner>/dian-shang-ping-tai-web`，依赖 test-and-package 与 frontend-build 通过） |

### 11.2 前端网关（nginx）
`deploy/nginx.conf` 承担：托管前端静态资源；反向代理 `/api/` → `app:8080`；反向代理 `/actuator/` → `app:8080`；SPA 路由回退到 `index.html`。外部统一访问 `web:80`，后端 8080 不直接对外。

### 11.3 容器服务清单与端口对照
| 服务 | 镜像 | 标准 SaaS 版 | 私有化版 |
| --- | --- | --- | --- |
| web（前端+网关） | `dian-shang-ping-tai-web` | `8080:80` | `8081:80` |
| app（API 主服务） | `dian-shang-ping-tai` | `18080:8080` | `28080:8080` |
| postgres | postgres:16-alpine | `15432:5432` | `25432:5432` |
| redis | redis:7-alpine | `16379:6379` | `26379:6379` |

| grafana | grafana/grafana:11.1.0 | `3000:3000` | `3001:3000` |

### 11.4 观测基线
- 后端已暴露 `health`、`info`、`prometheus` 端点（`management.endpoints.web.exposure.include`），Prometheus 指标导出已启用
- `deploy/prometheus.yml`：每 15s 抓取 `app:8080/actuator/prometheus`
- `deploy/grafana/provisioning/datasources/datasources.yml`：Grafana 启动自动注册 Prometheus 数据源（`http://prometheus:9090`）
- Grafana 默认关闭匿名注册（`GF_USERS_ALLOW_SIGN_UP=false`），管理员密码通过 `GRAFANA_ADMIN_PASSWORD` 注入
- 应用 HEALTHCHECK 与观测端点不依赖外部组件，容器编排可按 `service_healthy` 控制启动顺序

### 11.5 前端路由性能基线
- 前端路由已全部改造为按需动态导入（`component: () => import(...)`），主入口 chunk 由 838KB 降至约 119KB（gzip 46KB），28 个业务页面按需拆分加载

## 12. 部署前检查清单
- JDK 与 Maven 版本符合要求
- profile 与环境标识正确
- 数据库、Redis、MQ、对象存储连接参数已注入
- **生产环境必须注入全部密钥环境变量**：`SPRING_DATASOURCE_USERNAME/PASSWORD`、`APP_AUTH_TOKEN_SECRET`、`APP_AUTH_BOOTSTRAP_PASSWORD`、`GRAFANA_ADMIN_PASSWORD`（依赖 compose 占位默认值视为未加固）
- 审计日志、导出目录、对象存储路径可写
- Webhook 回调地址、开放平台密钥和通知配置已验证
- 备份、恢复、监控、告警链路已就绪
- 观测基线可达：`/actuator/health`、`/actuator/prometheus`、Prometheus 9090、Grafana 3000/3001
- 平台后台与租户前台访问入口已区分

## 13. 结论
部署文档的目标不是记录某一台机器的临时连接方式，而是定义一套可重复、可审计、可交付的软件部署基线。后续无论生成实施计划、上线清单还是私有化交付说明，都应以本文档为部署上位基线。
