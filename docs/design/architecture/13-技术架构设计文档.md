## 1. 文档目的
本文档从技术实现视角定义项目的技术框架、模块骨架、横切能力、数据与基础设施基线，以及当前工程快照。本文档用于承接《系统架构设计文档》的业务分层口径，作为后续详细设计、实施排期和研发落地的技术依据。

补充说明：

- 本文档描述的是技术基线与工程快照，不直接承担当前项目阶段判断。
- 当前真实进度、当前缺口和继续开发顺序，请优先看 `02 / 05 / 06` 三份主文档。

## 2. 技术架构总览
### 2.1 交付技术形态
项目交付技术形态定义为：

`模块化单体业务内核 + 标准应用分层 + 连接器集成框架 + 横切治理框架 + 可拆分部署组件`

### 2.2 技术分层
| 分层 | 职责 | 当前命名口径 |
| --- | --- | --- |
| 接口层 | HTTP API、平台管理接口、回调入口、开放接口、统一响应 | `Controller`、`ApiResponse` |
| 应用层 | 业务编排、事务边界、流程调度、跨模块协同 | `ApplicationService` |
| 领域层 | 领域模型、状态流转、业务规则、领域约束 | `model`、领域规则类 |
| 仓储抽象层 | 领域仓储接口、查询边界、持久化抽象 | `domain.repository` |
| 基础设施层 | JDBC、缓存、消息、对象存储、连接器、审计、幂等 | `infrastructure.persistence`、`infra` |
| 横切治理层 | 租户上下文、权限、审计、支持会话、Trace、风控 | `tenant`、`support`、`common`、`audit` |

## 6. 横切技术框架
### 6.1 租户与权限框架
- 所有租户级对象统一带 `tenant_id`。
- 接口入口统一解析租户上下文，再做角色、组织、店铺范围校验。
- 平台侧与租户侧接口命名空间物理分层。

### 6.2 审计与支持介入框架
- 所有高风险业务动作统一写入 `audit_log`。
- 平台支持介入统一依赖 `support_session`。
- 审计字段统一包含租户、组织、目标对象、操作人、结果和 `trace_id`。

### 6.3 Trace 与统一响应框架
- 请求链路统一使用 `TraceIdFilter` 透传 `trace_id`。
- 接口响应统一使用 `ApiResponse` 封装。
- 异常返回口径统一走业务异常与状态码约束。

### 6.4 幂等与重试框架
- 履约、通知、回调类对象统一保留幂等键或重试计数。
- Redis 作为幂等辅助和短期状态缓存。
- 失败任务必须支持重试和留痕，不允许静默吞掉关键异常。

## 8. 接口与集成架构
### 8.1 接口风格
- 租户业务接口：REST API
- 平台管理接口：REST API
- 开放平台接口：REST API + Webhook
- 回调入口：平台连接器适配接口

### 8.2 标准请求链路
当前主链路应统一理解为：

`HTTP Request -> Trace/Tenant Filter -> Controller -> ApplicationService -> Domain/Repository -> JDBC/InMemory -> ApiResponse`

### 8.3 集成框架要求
- 外部平台接入必须通过连接器抽象层，不直接把第三方协议散落到业务模块。
- 回调处理必须具备签名校验、幂等控制、失败重试和审计留痕。
- 开放平台能力必须与租户权限、配额、审计模型联动。

## 9. 部署与组件架构
### 9.1 当前部署基线
- 单体应用进程部署
- H2 用于本地快速验证
- PostgreSQL / Redis 用于联调和正式环境
- profile 包括：`default`、`postgres`、`tunnel-local`、`server-local`

### 9.2 交付部署组件
标准交付组件定义为：
- `web-api`：主 API 服务
- `job-worker`：定时任务与巡检服务
- `callback-worker`：回调消费与补偿服务
- `ai-worker`：模型编排与异步生成服务
- `postgres`：主业务库
- `redis`：缓存、幂等和短期状态控制
- `object-storage`：素材与导出文件
- `mq`：异步消息和削峰
- `observability stack`：日志、指标、告警和链路追踪
