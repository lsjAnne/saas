## 1. 文档目的
本文档用于定义项目数据库表结构设计基线，统一说明核心表清单、字段约束、索引策略、多租户边界和实施顺序，作为迁移脚本、接口开发、测试造数和运维验收的统一依据。

说明：
- 实际落地脚本以 `src/main/resources/db/migration` 下的迁移文件为准。
- 本文档重点解决“有哪些表、字段怎么设计、索引怎么建、哪些约束必须落地”。
- 状态枚举口径与字段业务含义应同步参考 [数据字典文档](03-数据字典文档.md) 和 [状态机说明文档](../architecture/02-状态机说明文档.md)。

## 2. 设计原则
- 先满足多租户 SaaS 隔离，再展开业务主链路设计。
- 先建主实体，再建关联实体，再建治理与分析实体。
- 核心业务表默认带 `created_at`、`updated_at`，必要时补充 `deleted_flag` 或禁用状态。
- 高频查询依赖组合索引，不把联表性能寄托在临时补救上。
- 平台侧治理数据和租户侧业务数据必须显式区分边界。
- 高风险字段默认支持脱敏、审计或异步导出，不直接走明文透出。

## 3. 命名与通用字段规范
### 3.1 命名规范
- 表名统一使用小写下划线，如 `tenant_subscription`、`product_source_mapping`。
- 主键统一使用 `id BIGINT`。
- 外键字段统一命名为 `<entity>_id`，如 `tenant_id`、`store_id`、`order_id`。
- 状态字段统一使用 `status` 或 `*_status`。
- 布尔字段统一使用 `*_flag`、`is_*`。
- 时间字段统一使用 `*_at`，如 `created_at`、`paid_at`、`expired_at`。

### 3.2 通用字段
| 字段 | 标准类型 | 说明 |
| --- | --- | --- |
| `id` | `BIGINT` | 表主键 |
| `tenant_id` | `BIGINT` | 多租户隔离最高业务边界 |
| `organization_id` | `BIGINT` | 组织或团队边界 |
| `store_id` | `BIGINT` | 店铺边界 |
| `status` / `*_status` | `VARCHAR(32)` | 状态枚举值 |
| `created_at` | `DATETIME` | 创建时间 |
| `updated_at` | `DATETIME` | 更新时间 |
| `*_json` | `JSON` / `TEXT` | 扩展配置或结构化明细 |
| `trace_id` | `VARCHAR(64)` | 全链路追踪标识 |
| `masked_flag` | `TINYINT(1)` | 是否已脱敏 |

### 3.3 通用约束
- 所有租户级业务表必须校验 `tenant_id`。
- 需要按组织协同时补充 `organization_id`。
- 需要按店铺经营时补充 `store_id`。
- 所有金额字段统一使用 `DECIMAL(12,2)` 或更高精度。
- 需要幂等的表必须补唯一键或幂等键，如履约、通知、外部回调。

## 5. 关键字段与约束要求
### 5.1 多租户与权限边界
- `tenant`、`organization`、`store` 三层边界要能完整映射到权限和数据范围。
- 直播、通知、审批、审计等治理能力不得省略 `tenant_id`。
- `live_account`、`live_concurrency_queue` 必须保证账号占用和并发申请的一致性，不允许同账号并发双占用。
- `live_scene_switch_record`、`live_manual_takeover_record`、`live_commitment_audit` 必须保留完整操作留痕字段，至少包含 `created_by`、`updated_by`、`created_at`、`updated_at`。
- `live_interaction_event`、`live_risk_event` 应支持幂等写入键，避免平台重复回调造成重复事件。
- 平台支持介入场景必须通过 `support_session_id` 与审计留痕关联。

### 5.2 金额与财务字段
- 所有金额字段统一使用 `DECIMAL(12,2)` 或更高精度。
- `finance_bill`、`billing_order`、`settlement_record` 需要保留状态、时间、外部流水号等追溯信息。
- 财务相关表不得直接硬删，应通过状态流转和归档控制。

### 5.3 幂等与重试字段
- `fulfillment_task.idempotency_key` 必须唯一。
- `notification_task.retry_count`、`fulfillment_task.retry_count` 必须有默认值并可审计。
- 外部回调或消息类对象必须保留 `trace_id`、`last_error_message`。

### 5.4 内容与隐私字段
- `customer_conversation`、`conversation_message`、`after_sale_record`、`audit_log` 需要考虑脱敏策略。
- `integration_credential.secret_key_mask` 不得存明文敏感密钥。
- `webhook_subscription.secret_token` 应结合加密或安全存储方案。

## 6. 标准建表顺序
1. 先建 `tenant`、`organization`、`organization_member`、`subscription_plan`、`tenant_subscription`、`usage_quota`、`billing_order`、`invoice_request`、`support_session`、`audit_log`。
2. 再建 `store`、`channel_account`、`candidate_product`、`supplier`、`product_draft`、`product`、`product_source_mapping`、`sku`、`sku_mapping`、`inventory_snapshot`、`replenishment_task`、`content_asset`。
3. 然后建 `order_main`、`order_item`、`fulfillment_task`、`logistics_record`、`exception_task`、`customer_service_ticket`、`after_sale_record`。
4. 再建 `customer_conversation`、`conversation_message`、`faq_knowledge`、`live_account`、`live_plan`、`live_session`、`live_script`、`live_risk_event`、`live_concurrency_queue`、`live_interaction_event`、`live_scene_template`、`live_scene_switch_record`、`live_manual_takeover_record`、`live_commitment_audit`、`automation_rule`、`campaign_activity`、`coupon_template`、`member_profile`、`member_tag`、`finance_bill`、`settlement_record`。
5. 最后建 `notification_task`、`approval_instance`、`plugin_app`、`integration_credential`、`webhook_subscription`、`metric_daily_snapshot`。

## 7. 迁移与验收要求
### 7.1 迁移要求
- 每个阶段独立迁移文件，避免一个脚本承载过多变更。
- 变更脚本命名与版本号统一纳入迁移目录维护。
- 涉及高频表索引调整时，必须评估锁表与执行窗口。

### 7.2 验收清单
- 表、字段、默认值、索引、唯一键是否全部落地。
- `tenant_id` 是否覆盖所有租户级表。
- 高风险表是否补齐审计、脱敏或幂等控制字段。
- 主链路查询是否命中预期索引。
- 跨租户查询、导出、回调、缓存是否有串租户风险。

## 9. 结论
数据库设计不能只满足“能存数据”，还必须同时满足多租户隔离、主链路执行、经营分析、审计留痕和商用交付要求。

这份文档已经替代原乱码版本，当前可作为库表设计、迁移实施和测试验收的正式基线。
