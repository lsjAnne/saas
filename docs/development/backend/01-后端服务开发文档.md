## 1. 文档目的
本文档用于指导后端开发工程师完成模块划分、领域服务、任务编排、接口约束、权限治理和审计留痕设计，确保后端实现能够支撑商用 SaaS 交付。

## 2. 后端建设目标
- 支撑 `SaaS 平台底座 + OMS + SRM + ERP 基础能力 + CRM + WMS/TMS + BI` 主链路稳定运行
- 保证接口可追踪、可审计、可重试、可扩展
- 让模型能力以增强层方式接入，不替代主系统状态流转
- 为后续服务拆分、开放平台和私有化交付预留空间

## 4. 分层设计
### 4.1 推荐分层
- Controller：对外 HTTP 接口层
- Application Service：跨模块编排层
- Domain Service：领域规则层
- Repository：持久化访问层
- Connector：外部平台接入层
- Job / Consumer：异步任务与消息消费层

### 4.2 设计原则
- Controller 不承载复杂业务逻辑
- Domain Service 不依赖前端字段结构
- Connector 统一处理第三方限流、签名、重试和错误码映射
- 跨模块编排优先通过应用服务、领域事件或补偿任务完成
- 模型结果必须经过业务规则和风控校验后才能进入正式状态

## 6. 事务与一致性设计
- 单模块核心写操作使用本地事务
- 跨模块状态变更使用事件驱动、任务补偿或事务外盒模式
- 对外回调写入必须具备幂等能力
- 订单履约、消息通知、订阅状态变更、模型异步生成必须可重试

## 8. 接口规范
### 8.1 返回结构
- `code`
- `message`
- `data`
- `traceId`

### 8.2 状态约束
- 状态流转以状态机与系统设计文档为准
- 状态非法时必须返回明确错误码
- 不允许通过接口直接跳过中间状态

### 8.3 幂等要求
- 履约任务创建
- 物流回传
- 开放平台回调
- 订阅状态变更
- 账单生成

### 8.4 租户上下文要求
- Controller 层必须从登录态、Token 或网关透传信息中解析租户上下文
- Application Service 不接受来自普通租户前端的任意 `tenantId` 覆盖
- 平台接口访问租户数据时必须校验平台角色、支持会话和访问时效
- Repository 查询模板默认带 `tenant_id` 条件，只有平台后台白名单仓储允许跨租户检索

## 9. 权限与数据隔离
- 租户级隔离优先
- 组织级数据范围其次
- 店铺级权限按角色范围控制
- 敏感操作必须二次鉴权或审批
- 权限校验顺序固定为：登录态 -> 租户上下文 -> 角色权限 -> 组织范围 -> 店铺范围 -> 业务状态
- 缓存 Key、消息 Topic、异步任务参数、导出任务快照必须包含 `tenant_id`
- 平台支持介入必须单独建模支持会话，不得复用普通租户登录态

## 10. 风控与审计
- 高风险内容发布前必须校验
- 高风险订单、售后、结算动作进入审批
- 回复建议、脚本生成、价格异常、订阅变更必须留痕
- 审计日志至少记录操作人、时间、目标对象、变更结果、来源模块
- 审计日志、开放平台调用日志、任务日志统一要求记录 `tenant_id`、`organization_id`、`trace_id`、`source_module`
- 日志查询接口默认按当前租户过滤；平台全局检索能力必须单独实现并记录查询原因
- 所有导出任务必须异步化并记录下载人、下载 IP、下载时间和过期时间

## 12. 后端测试要求
- 领域服务必须有单元测试
- 核心接口必须有集成测试
- 回调、重试、并发、幂等必须有自动化测试
- 多租户隔离、支持会话、订阅到期、配额不足必须单独回归

## 14. 结论
后端不是只把接口做出来，而是要把系统边界、编排逻辑、幂等补偿、权限治理和审计留痕一次设计清楚，否则平台很难支撑后续商用版扩展。
