## 3. 当前标准包结构

### 3.1 完整业务模块模板

当前大多数业务模块已稳定采用下面这种结构：

```text
{module}
├─ application
├─ controller
├─ domain
├─ dto
├─ infrastructure
└─ model
```

适用示例：

- `product`
- `supplier`
- `inventory`
- `order`
- `fulfillment`
- `servicecase`
- `saas`
- `openplatform`
- `contentasset`

### 3.2 轻量模块模板

部分模块当前是轻量聚合或治理入口，只保留必要分层：

```text
{module}
├─ application
├─ controller
└─ 可选的 dto / config / security
```

适用示例：

- `dashboard`
- `recommendation`
- `system`
- `tenant`

说明：

- 轻量模块不是“不规范”，而是当前复杂度还没到需要完整 `domain / infrastructure / model`。
- 后续只有在复杂度显著上升时，才继续扩层。

## 4. 各模块到底放什么

### 4.1 `common`

用于放跨模块通用能力：

- `api`：统一响应结构
- `exception`：通用异常
- `trace`：链路追踪
- `web`：Web 层通用处理

### 4.2 `infra`

用于放基础设施实现：

- 当前已存在 `redis`
- 后续数据库底层、对象存储、消息等基础设施优先放这里

### 4.3 `tenant`

用于放租户上下文和权限辅助：

- 租户上下文
- 平台/租户权限判断
- 鉴权拦截器和注解
- 租户上下文查询入口

### 4.4 `system`

用于放系统级聚合能力：

- 阶段 13 的 readiness / observability / delivery 相关配置与聚合
- 系统级 DTO
- 系统摘要接口

### 4.5 平台治理层模块

适合放平台运营、SaaS 治理和开放能力：

- `admin`：平台管理与租户运营视角
- `auth`：登录与身份桥接
- `saas`：套餐、订阅、配额、停复服
- `openplatform`：开放平台应用、scope、凭据、日志、Webhook
- `approval`：审批流
- `notification`：通知任务
- `support`：平台支持工作台
- `audit`：审计相关实现

### 4.6 核心业务域模块

适合放经营主链路和增强域：

- `organization / store / supplier / product / contentasset`
- `inventory / order / fulfillment / exceptioncenter`
- `servicecase / qa / live / campaign / member / finance`
- `dashboard / recommendation / rule`

## 5. 新增代码怎么放

后续新增代码统一按下面规则落位：

1. 先判断是不是横切能力。
   横切能力进 `common / infra / tenant / system`。
2. 再判断是不是平台治理能力。
   平台治理能力进 `admin / auth / saas / openplatform / approval / notification / support / audit`。
3. 再判断是不是具体业务域能力。
   具体业务域能力进入已有业务模块，不新开含义重复的顶层包。
4. 如果目标模块已经是完整业务模块模板，优先补进 `application / controller / domain / dto / infrastructure / model`。
5. 如果目标模块当前是轻量模块模板，不要为了形式整齐先补空目录。

## 6. 推荐阅读顺序

当你需要看后端代码树时，建议按下面顺序进入：

1. `tenant / system / common / infra`
2. `saas / auth / openplatform / admin`
3. `organization -> store -> product -> supplier -> inventory -> order -> fulfillment`
4. `servicecase / qa / live / campaign / member / finance`
5. `dashboard / recommendation / rule / contentasset`

## 7. 测试代码树对应关系

测试根路径为 `backend/src/test/java/backend`。

当前测试目录基本按业务模块镜像组织，例如：

- `admin`
- `auth`
- `campaign`
- `contentasset`
- `inventory`
- `openplatform`
- `order`
- `saas`
- `system`

规则：

- 新增模块测试优先按模块同名目录放置。
- Controller 测试优先跟业务模块走，不单独再造一套横向测试树。

## 8. 资源目录规则

当前资源目录统一放在：

```text
src/main/resources
├─ application.yml
└─ db/migration
```

规则：

- 配置统一进 `application.yml` 及其后续 profile 配置。
- 数据库迁移统一进 `db/migration`。
- 当前迁移脚本已扩展到 `V025`，后续新增迁移继续按顺序追加。
