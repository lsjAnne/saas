## 1. 文档目的
本文档用于描述当前真实前端代码树、模块拆分方式、状态管理、接口接入和页面落位规则，避免只看目录名猜前端结构。

补充说明：

- 当前仓库已存在真实前端工程 `frontend/`。
- 本文档的定位是实现约束与真实代码树说明，不是“待建设前端”的计划文档。

## 2. 前端建设目标

- 页面入口清晰
- 业务域边界清晰
- 组件复用路径清晰
- 接口接入路径清晰
- 能支撑 `OMS / SRM / ERP / CRM / BI / SaaS / 开放平台` 并行开发

## 3. 当前真实代码树

### 3.1 `frontend/src` 顶层结构

```text
frontend/src
├─ app
│  ├─ layouts
│  ├─ router
│  └─ styles
├─ components
│  ├─ cards
│  ├─ feedback
│  ├─ planning
│  └─ shell
├─ features
├─ pages
├─ services
│  └─ http
├─ stores
│  └─ authStore.ts
└─ utils
```

### 3.2 各目录职责

- `app`：应用壳层、布局、路由、全局样式入口
- `components`：跨模块复用组件
- `features`：按业务域拆分的功能实现
- `pages`：路由页面容器，负责拼装业务模块
- `services`：统一接口访问层
- `stores`：全局共享状态
- `utils`：纯工具函数

### 4.2 当前结构结论

当前前端并不是“页面全堆在一起”，而是：

1. `pages` 负责路由级页面容器
2. `features` 负责业务域功能
3. `components` 负责复用展示组件
4. `services` 负责接口访问
5. `stores` 负责少量全局共享状态

后续新增页面或新需求，优先补到现有 `features/<业务域>` 下，不新开含义重叠目录。

## 5. 前端落位规则

### 5.1 页面代码放哪里

- 路由页面容器放 `pages`
- 某个系统域的主要业务实现放 `features/<业务域>`
- 纯复用卡片、提示、布局壳层放 `components`

### 5.2 接口代码放哪里

- 所有 HTTP 请求统一从 `services/http` 承接
- 不在 `pages` 或 `components` 里散落裸请求

### 5.3 状态代码放哪里

- 登录态等全局共享状态放 `stores`
- 局部交互状态优先放组件内部或 `features` 内部

## 6. 路由与壳层规则

### 6.1 `app`

`app` 目录当前负责：

- `layouts`：应用布局壳层
- `router`：路由定义
- `styles`：全局样式入口

规则：

- 全局框架能力优先放 `app`
- 不把具体业务逻辑塞进 `app`

### 6.2 `pages`

`pages` 负责路由级容器，主要职责：

- 读取路由参数
- 组织页面布局
- 组合一个或多个 `features`

规则：

- `pages` 不承载过重业务逻辑
- 复杂业务判断下沉到 `features`

## 7. 推荐阅读顺序

当你需要看前端代码树时，建议按下面顺序进入：

1. 先看 `app/layouts` 和 `app/router`
2. 再看 `pages`
3. 再看对应业务域的 `features/<模块>`
4. 需要找复用组件时再进 `components`
5. 需要找接口时进 `services/http`
6. 需要找全局登录状态时进 `stores/authStore.ts`

## 8. 后续新增代码怎么放

1. 新页面先判断是否已有对应 `features` 业务域。
2. 有现成业务域时，优先补到现有 `features/<业务域>`。
3. 没有现成业务域时，先判断是不是现有业务域的子能力，不急着新建目录。
4. 新增纯复用展示组件，放 `components`。
5. 新增全局样式、路由、布局规则，放 `app`。
6. 新增接口请求，统一走 `services/http`。

## 9. 当前整理结论

当前前端代码树已经具备“应用壳层 + 页面容器 + 业务域 feature + 复用组件 + 服务层 + store”的清晰分层。后续整理重点不应是随意搬目录，而应是继续按现有分层补代码，避免重新打乱边界。
