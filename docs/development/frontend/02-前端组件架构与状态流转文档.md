## 1. 文档目的
本文档用于把前端从“页面清单”进一步落到“组件树、状态流、查询流、交互流”的实现层，确保多人并行开发时页面不会因为状态散乱、组件边界不清而失控。

补充说明：

- 当前仓库已存在真实前端工程 `frontend/`。
- 本文档描述的是当前实现应遵守的组件和状态流规则，不是纯原型阶段的前置设想。

## 2. 组件分层规则
### 2.1 分层定义
- `app`：应用入口、路由、布局骨架、全局守卫
- `pages`：页面容器，负责场景拼装
- `features`：业务功能块，负责领域交互和局部状态
- `components`：通用 UI 组件
- `services`：接口和查询封装
- `stores`：跨页面共享状态
- `schemas`：表单和接口校验
- `utils`：工具方法

### 2.2 拆分原则
- 页面容器不直接写复杂接口调用细节。
- `features` 允许组合多个接口，但不直接依赖全局布局。
- 通用组件不感知具体业务接口。
- 表格、筛选器、表单、步骤流优先沉淀为可复用组件。

## 4. 状态流转设计
### 4.1 全局状态
- 登录态
- 租户上下文
- 当前组织
- 当前店铺范围
- 菜单权限
- 消息未读数

### 4.2 页面状态
- 列表筛选条件
- 分页与排序
- 抽屉、弹窗开关
- 当前选中记录
- 当前步骤条状态

### 4.3 实时状态
- 直播运行状态
- 问答会话更新
- 异常数量变化
- 通知提醒

### 4.4 状态流原则
- 服务端真相状态优先由查询层托管。
- 临时交互状态优先组件内消化。
- 跨页面共享但非服务端真相的状态才进入 `stores`。
- 所有状态恢复逻辑必须显式，禁止页面刷新后出现“假成功”。

## 5. 查询与缓存架构
### 5.1 查询分层
- 列表查询：分页、筛选、排序
- 详情查询：按主键加载单条数据
- 聚合查询：驾驶舱卡片、统计看板、运行态摘要
- 实时查询：长轮询、短轮询或推送

### 5.2 缓存原则
- 列表页切换分页允许短时缓存。
- 提交写操作后必须精确失效关联查询。
- 配额、直播状态、审批待办等高动态数据不得长时间缓存。
- 多租户上下文变化时必须整体失效与租户绑定的缓存。

## 6. 关键交互状态机
### 6.1 商品发布
`草稿中 -> 校验中 -> 待确认 -> 发布中 -> 已发布/发布失败`

### 6.2 问答接管
`AI建议中 -> 风控命中 -> 人工接管 -> 已回复 -> 已归档`

### 6.3 直播开播
`计划中 -> 校验中 -> 待开播 -> 直播中 -> 暂停中/已结束/异常中断`

## 7. 页面事件流设计
### 7.1 订单履约事件流
1. 用户点击订单详情。
2. 页面加载订单主信息、履约记录、物流时间线。
3. 若存在异常，显示建议动作和人工处理入口。
4. 用户执行处理后，失效相关查询并刷新详情。

### 7.2 问答处理事件流
1. 买家会话进入列表。
2. 页面加载消息流和 建议。
3. 风控命中则显示显著警告并禁用直接发送。
4. 人工接管后记录处理结果并刷新会话状态。

### 7.3 直播执行事件流
1. 用户打开直播计划。
2. 页面加载脚本、商品池、配额状态。
3. 发起开播时先校验账号占用和套餐并发。
4. 开播成功后切入实时状态面板。
5. 异常发生时显示接管或暂停入口。

## 8. 表单架构建议
- 筛选表单、配置表单、审批表单、创建表单分开封装。
- 复杂表单采用 `schema + field-config` 驱动，避免页面中硬编码校验。
- 所有高风险表单提交前必须有摘要确认层。
- 异步保存结果必须明确展示“保存成功、已生效、待审批”三种不同状态。

## 9. 联调约束
- 前端只信后端返回的权限范围，不根据本地角色名称自行推导最终权限。
- 任何涉及租户切换、组织切换、店铺切换的交互，都要在 UI 上明确展示当前上下文。
- 平台支持人员只有在有效支持会话（support session）内，前端才允许展示受控详情页入口。

## 10. 测试重点
- 路由守卫是否正确阻断无权限页面。
- 切换租户、组织、店铺后查询缓存是否正确失效。
- 高风险动作二次确认是否与后端状态一致。
- 直播、问答、审批等高动态页面是否存在状态残留。
