- `001-260` 主线功能已经完成到“本地可开发、可测试、可继续扩展”的状态。

### 4.4 已落代码的交付骨架

- GitHub Actions、双 compose 配置、交付 readiness 视图已具备基础骨架。
- `delivery-readiness` 已增加本地可诊断的外部接线探测快照：
  - ERP / WMS / BI / routing 走 HTTP 可达性探测
  - RabbitMQ 走 TCP 建连探测
- `delivery-readiness` 现已继续把双交付验收地址从“只看 baseUrl/verifiedAt”推进到“结构化本地 HTTP probe”：
  - 标准 SaaS / 私有化环境同步暴露 `protocol/reachable/detail`
  - `acceptance.ready` 只有在验收地址配置完整且本地探测可达时才为 `true`
- 双交付验收证据现已继续从“只看 verifiedAt 是否存在”推进到“验证证据是否仍然新鲜有效”：
  - `standardSaas/privateDeployment` 同步暴露 `verificationFresh/verificationStatus/verificationAgeDays`
  - 超过 `app.delivery.acceptance-evidence-max-age-days` 的旧验收记录会被判定为 `stale`
  - `acceptance.ready` 现在要求“配置完整 + verification fresh + probe reachable”
- 发布链路本地资产现已纳入 `delivery pipeline` 门禁：
  - `backend-delivery.yml`、`docker-compose.saas.yml`、`docker-compose.private.yml` 会作为结构化资产快照进入 `pipeline`
  - 缺文件或缺关键 marker 时会直接把 `pipeline.ready` 判为 `false`
  - `release-readiness` 与开放平台 `delivery/readiness` 会同步把这些资产缺口作为阻塞原因输出
- 发布凭据来源现已进入 `delivery pipeline` 结构化诊断：
  - `releaseKeyControl`、`registryAuthControl`、`githubPublishingControl`、`canaryControl` 会同步暴露 `value/sourceType/sourceName/defaultValue/trusted/status/detail`
  - 现在不仅能看见发布开关是否打开，也能区分默认值、显式可信配置与解析式非可信来源
  - 当前这层仍属于“本地发布凭据来源可读”，不是“真实生产发布账号与仓库权限已验收”
- 新增 `stage13-local` 本地可运行闭环：
  - `ExternalDependencyObservabilityConfiguration` 会在本地启动 HTTP/TCP probe mock，覆盖 ERP/WMS/Tax/BI/Routing/Messaging、callback worker、observability 以及 GitHub/registry/双交付验收地址
  - `application.yml` 与 `docker-compose.saas.yml` / `docker-compose.private.yml` 默认注入本地闭环所需 endpoint、gate 与 verification 时间
  - 目标是让本机直跑和 compose 验证都能在不伪造真实 GitHub、registry 或第三方账号的前提下跑通 stage-13 本地门禁
- 开放平台 `GET /api/open/external/delivery/readiness` 现已同步返回 `blockingReasons`：
  - 只按当前 overview 已暴露的 `pipeline / externalIntegrations / acceptance` 三块证据生成
  - 调用方不再只知道 `pipelineReady/externalIntegrationsReady/acceptanceReady`，也能直接看到卡点
- `release-readiness` 的 `external_integration_readiness` 已同步消费本地探测结果：
  - 在配置完整的基础上补充 `probe reachable x/y` 证据
- 观测栈 endpoint 现已继续补齐来源诊断并进入真实 gate：
  - `logAggregation/trace/alertRouter/dashboard` 会同步暴露 `sourceType/sourceName/defaultValue/trusted/status`
  - 高优先级 property source 若只是 placeholder 解析，不会再误判成下层显式可信配置
  - `release-readiness`、管理侧 `observability-readiness`、开放平台 `observability-readiness` 与 actuator `externalDependencies` 会统一把 `must be explicitly configured` 作为真实阻塞原因
- `release-readiness` 的 `dual_delivery_acceptance` 现已同步消费双交付验收地址的本地 probe 结果：
  - detail 显式输出 `probe reachable 2/2`
  - 标准 SaaS / 私有化验收地址任一不可达时直接阻塞放行
- `observability-overview`、`actuator/info`、`actuator/health` 已同步暴露本地 probe 快照：
  - 新增 `externalIntegrationConnectivity`，返回 `configuredCount`、`reachableCount` 与逐系统探测明细
- 当前已经可以表达“配置是否齐”“门禁是否满足”，但还不等于真实外部环境已全部联通。
